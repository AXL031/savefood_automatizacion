# Operación integrada · ampliación autorizada 27-10-2026

Autor: Codex por solicitud expresa del usuario. Cueva coordina; Rojas producción/tienda, Sanchez ventas/UI, Vera inventario/promociones, Aguirre proveedores/recepción. Amplía el alcance histórico: confirmar producción consume ingredientes y crea productos; ventas internas consumen productos y agregan revisiones de ventas; tienda conserva ventas fuera de ML. No hay pagos reales ni negociación automática.

## Contrato

- `/operaciones/producciones`: POST autenticado Admin/Operador, plan_id, fecha, clave_idempotencia, lineas[{producto_id,cantidad,fecha_caducidad}]. Usa receta inmutable del plan, permite tandas hasta pendiente. Misma clave/actor/contenido recupera; distinto contenido 409. Stock y auditoría en transacción, sin commits de servicios. No producir por encima del plan ni descontar ingredientes al vender.
- `/operaciones/ventas`: POST Admin/Operador, fecha, clave y líneas; FEFO, lotes vigentes con fecha conocida, no saldo negativo. Venta interna agrega revisión a Ventas y solicita reevaluación; tienda no altera Ventas/ML.
- `/operaciones/resumen`: GET autenticado, inventario, pendientes de planes, producciones/ventas, fichas, configuración, promociones y recepciones.
- `/operaciones/configuracion`: PUT Admin, productos vigilados, regla existente, reloj ACTUAL/ESCENARIO. Revisión cada 600 s por Beat; consulta stock vigente, no exige ajuste manual nuevo. Guardar no envía mensajes. Sugerencia única por lote/regla/fecha; rechazo conserva motivo. Solo aprobación Admin publica; se termina por agotamiento/vencimiento.
- `/operaciones/avisos`: GET Admin, persistentes, leídos independientes de resolución; PATCH lectura. Recepción parcial/defectuosa conserva incidencia; resolución interna Admin con motivo, sin Telegram de reposición.
- `/operaciones/pedidos/{id}/enlace`: POST Admin; token aleatorio exclusivo con hash persistido, 1 h real, solo una respuesta, GET no cambia estado. URL pública fija de configuración, token nunca en logs ni DNI en URL. DNI no se usa como prueba de identidad. Nueva emisión invalida anterior y conserva auditoría.
- `/proveedor/pedidos/{token}` GET/POST público: muestra solo pedido asociado; POST ACEPTAR/RECHAZAR con nombre y compromiso, validación de vencimiento en servidor; repetición idéntica recupera, contradictoria 409. Propuesta cancelada no admite aceptación. Sin respuesta → cerrar/aviso por Beat. Se separa respuesta de envío y recepción.
- `/operaciones/recepciones/{id}` POST Admin/Operador: solo pedido aceptado; formulario con pendientes, 0..pendiente, descripción obligatoria al reducir, fecha/lote/caducidad. Cero aceptado no genera movimiento. Se reaprovecha recepción existente para líneas positivas y se registra incidencia en la misma transacción. No hay compra automática de reposición.
- Tienda real conserva `/tienda/catalogo`, `/stock`, `/carrito/cotizar`, `/pedidos`, `/pedidos/{id}` con contrato ADR-009; pago simulado con whitelist estricta, no tarjeta en API. Fichas/precios versionados en auditoría, publicación Admin; importación CSV atómica. Sesión Google conservada; cuenta cliente local con contraseña para pruebas habilitable explícitamente (sin falsificar Google).

## Entornos y aceptación

Docker sigue siendo instalación completa. Acceso gratuito de demostración con reverse proxy de Next hacia API y Cloudflare Quick Tunnel, sin SLA y dependiente de PC encendida. Render es configuración opcional de pago, no se crean recursos cobrables sin presupuesto. Secretos de instalación (PostgreSQL, JWT y Telegram) en `.env*`/`.tmp`, nunca documentación pública. Por solicitud expresa posterior del usuario se publican solo los tres accesos mock en `datos_carga/cuentas_demo.json`; el lanzador los usa en instalaciones nuevas con claves PostgreSQL/JWT propias, sin cambiar credenciales ya existentes. No reutilizarlos con datos reales. Migración aditiva 0020 después de 0019; no reescribir migraciones aplicadas. HTTP JSON con datos/error, 401/403/409/410/422, permisos en servidor.

Pruebas obligatorias: rollback completo, claves repetidas/distintas, tandas y FEFO, separación tienda/ML, caducidad, precio cambiado, enlace vencido/repetido, recepción 0/parcial/total, alertas idempotentes, aprobación/publicación y ventana de diez minutos. SQLite prueba reglas/transacciones; PostgreSQL prueba locks reales; no acreditar servicios/mensajes externos con mocks.
